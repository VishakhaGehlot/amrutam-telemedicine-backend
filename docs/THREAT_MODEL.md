# Security Checklist and Threat Model

## Data classification
| Class | Examples | Controls |
|---|---|---|
| Public | Verified doctor name, specialization | Publish only approved fields |
| Internal | Operational metrics, request IDs | Access control, retention |
| Personal | Email, phone, DOB | Least privilege, TLS, restricted logs |
| Sensitive health data | Consultation reason, prescription items | TLS + encrypted disks/backups, strict authorization, audit, minimal retention |

## Attack surface
- Public REST endpoints: registration, login, doctor search, health probes.
- Authenticated endpoints: profile, availability, booking, consultation and prescription actions.
- Database credentials and JWT signing secret.
- CI pipeline, container image and deployment environment.
- Future integrations: payment gateway, video consultation, email/SMS and async workers.

## Threats and mitigations
| Threat | Risk | Mitigation in repo | Remaining production work |
|---|---|---|---|
| SQL injection | Read/write unauthorized data | Parameterized SQL | Add SAST/DAST and review dynamic query additions |
| Password theft | Account takeover | bcrypt cost 12; minimum 12-char password | MFA enrollment, breached-password checks, credential-stuffing controls |
| JWT theft | Impersonation | Short-lived HS256 token, explicit algorithm | Secret manager, rotation, refresh/session revocation strategy |
| Broken access control | Cross-patient/doctor data leak | Role middleware; doctor ownership checks on status/prescriptions | Comprehensive object-level authorization tests |
| Double booking | Conflicting appointments | DB transaction, row lock, unique slot | Concurrency/load tests |
| Replay / duplicate write | Duplicate bookings | Idempotency key + stored response | Request fingerprint and retention policy |
| Brute force / DoS | Service unavailable | General rate limit, JSON body cap | Per-account login throttling, WAF, distributed rate limiter |
| Sensitive logs | Health-data exposure | Logs avoid request body and token values | Central log redaction and retention controls |
| Dependency compromise | Supply-chain risk | npm lockfile to be generated by npm install; CI workflow | Commit lockfile, Dependabot, npm audit, image scanning/SBOM |
| DB compromise | Exposure of health data | Least-privilege DB user is recommended | Production DB role, TLS, KMS-backed encryption, key rotation |
| Backup theft | Data disclosure | Strategy documented | Encrypted backups, restore tests, isolated credentials |

## Key management and encryption
Use HTTPS/TLS at the ingress and TLS to managed PostgreSQL. Use provider-managed encryption at rest for disks, database and backups. Store JWT/database secrets in a secret manager, rotate on a defined schedule, and never commit `.env`. Do not invent custom cryptography. Field-level encryption for especially sensitive values should use a managed KMS and a versioned key identifier; this is not implemented in the assignment starter.

## Compliance note
This is a learning/assignment reference, not a certified compliant medical system. Before real patient data is used, perform a legal/privacy review for applicable Indian healthcare and personal-data obligations, define consent and retention, and complete security testing.
